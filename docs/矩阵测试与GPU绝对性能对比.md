## 0. 结论速览

1. **矩阵测试 56/56 PASS**，自研在 **B ≤ 64 的 28/28 点全胜 CANN 原生算子（1.42×–5.46×）**，
   在 **B ≥ 4096 的 14/14 点全输（0.20×–0.91×）**；总比分 **35 : 21**。
2. **vs 网上的 GPU 工作（cuFFT @ Tesla V100，同为 fp32 C2C 1D、同 batch=10000）**：
   自研慢 **9.9×（n=4096）～ 42.6×（n=64）**；等效带宽 **18–80 GB/s vs 562–804 GB/s**。
   cuFFT 在 n=4096 处达到 **795 GB/s ≈ V100 公开 HBM2 规格 900 GB/s 的 88%** —— 它是**内存带宽受限**的。
3. 差距的根因与 §10.2 的结论一致：**不是内存搬运，是矢量算子发射**。
   我们 `n=4096` 的 `#op = 2012`、`12 ns/op`，仅这一项就占 n=4096/B=4096 实测的 **63%**；
   在 radix-2 结构内 `#op` 已无低成本下降空间（§8.1–§9.5），要逼近带宽墙只能靠
   **`D>1` 批折叠 / 更深的流水重构**（§10.3 第 5 条，尚未做）。

> **口径统一说明**
> - **等效带宽** = `16n × batch / 时间`（一次复变换最少要读 `8n` 字节、写 `8n` 字节），与 §10.1 同口径。
> - **GFLOPS** = `5n·log2(n)·batch / 时间`（业界通用的 FFT 计数约定）。
> - **自研** 列为 `fft_check` 的 **reps=30 均值**（含启动 + 回同步，与 η 标定同口径）。
> - **cuFFT/cuButterfly** 列为其原文的 **resident kernel time**（不含 host 启动）。
>   两者不是完全同口径 —— 自研那 ~21 µs 的启动开销在小 batch 时会放大差距，见 §2.4。
> - **本卡 HBM 峰值未测**：`aclrtMemcpy(DEVICE_TO_DEVICE)` 探针只跑出 **6.7 GB/s**
>   （`build/bw_probe 256 20`），显然走的不是真 HBM DMA 通路，不能当峰值用，故本文**不引用本卡峰值**作分母。

- 自研在 B ≥ 1024 后稳定在 **~300 GFLOPS**（launch 已摊平），约为 cuFFT@V100 的 **1/10**。
- **同卡的 CANN 原生算子也只有 330–579 GFLOPS**，与 GPU 差 5–9× ——
  说明这部分差距**不只是我们实现的问题，也有该卡 FFT 算子本身的水平**；
  我们相对同卡原生的落后幅度（B=4096 时 0.72×）远小于相对 GPU 的落后幅度（10×）。

## 3. 差距定位与下一步

### 3.1 不是"白搬数据"

`fft_radix2.cpp:70-79` 把旋转因子与三张索引的 `DataCopy` 放在批循环外，
每批 GM 流量恰为 `16n` 字节 = 理论下限（§10.2）。所以上面的"等效带宽"不是被多余搬运稀释的。

### 3.2 是"矢量算子发射"

按 §8.5 标定的权重回算 n=4096 / B=4096（每 block 86 批）：

| 组成 | 耗时 | 占比 |
|---|---:|---:|
| `#op = 2012` 次矢量算子调用 × `12 ns` × 86 批 | 2,076 µs | **63%** |
| `elems = 270336` × `0.050 ns` × 86 批 | 1,162 µs | 35% |
| launch + 回同步 | 21 µs | 1% |
| **合计（模型）** | **3,260 µs** | 99% of 实测 3,288 µs |

而 `#op` 在 radix-2 结构内已经被榨干：

- K 择优已最优（§8.2：K=64/128 反而更差）
- 屏障降级无收益（§9.2）
- radix-4/8 融合会让 `#op` **+13%/+29%**（§9.4，已否决）
- 输入双缓冲 UB 放不下（§9.5：只剩 7.3 KiB）

### 3.3 唯一还没动的杠杆

**`D>1` 批折叠 / `Ts` 折叠**（§10.3 第 5 条）：把 batch 当成一个显式维度折进矢量算子，
让一次算子调用覆盖 `D` 批 —— `#op` 按 `D` 倍下降，而元素访存数不变，
正好打击占 63% 的那一项。这是把 300 GFLOPS 往 3000 GFLOPS（带宽墙）推的唯一结构性手段。

次要项：`launchUs = 20.812` 在小 batch 区明显偏大（B=1 时实测 28 µs，模型给 26.4 µs 但 kernel 只占几 µs），
可以给 η 按 batch 分档固定开销。

### 3.4 msprof 实测佐证（2026-09-29，详见 `docs/trace与profile诊断-小尺寸与大尺寸.md`）

`--aic-metrics=PipeUtilization` 直接给出的**管线占空比**，与上面的 η 权重模型互相印证：

| | 自研 `kfft_fwd` | 原生 `BatchMatMulV2` | 原生 `Transpose` |
|:---|---:|---:|---:|
| 执行单元 | AIV 矢量 | **AIC 矩阵** | AIV 矢量 |
| **`aiv_vec_ratio`（矢量管线）** | **0.815**（0.786–0.819） | — | 0.327 |
| `aiv_scalar_ratio`（标量管线） | **0.203** | — | 0.193 |
| **`aiv_mte2/mte3`（GM 搬运）** | **0.040 / 0.027** | 0.973 | 0.244 / 0.418 |
| **`cube_utilization`** | **0.000** | **83.0** | — |

三个直接结论：

1. **不是内存墙**：GM 搬运管线只忙 4%，矢量管线忙 **81.5%** —— §3.2 的 `#op` 结论由硬件计数器证实。
2. **Scalar 管线 20.3%** 是 η 模型没单独建模的一块，属"白捡"的优化空间。
3. **Cube 矩阵单元 100% 闲置**，而原生 62% 的时间花在 cube 利用率 83% 的 matmul 上
   （`4096 = 16³` → 原生是 3 个 16 点 DFT 批量复矩阵乘 + 2 次转置，共 5 次提交，2,334 µs；
   我们是单个融合矢量 kernel，3,252 µs，慢 **1.39×**）。

**小尺寸侧的设备侧拆账**（同一批 profile）：

| batch | blocks = min(batch,48) | **设备时长** | 预测 = 最大批数 × 38 µs | AIV 有效占用 |
|---:|---:|---:|---:|:---|
| 1 | 1 | **38.7 µs** | 1 × 38 ✓ | **1/48 = 2%** |
| 64 | 48 | **76.1 µs** | 2 × 38 ✓ | 67%（16 核做 2 批、32 核做 1 批） |
| 4096 | 48 | **3,252.0 µs** | 86 × 37.8 ✓ | ~99% |

→ **n=4096/B=1 的 66.3 µs = 设备 38.7 + host 27.6**，而 cuFFT 是 11.99 µs。
**设备侧慢 3.2×（因为只用了 1/48 个核），host 侧多 27.6 µs**，两笔账要分开算。

## 4. 测量注意事项（读数时请先看这一节）

1. **共享机器、噪声不小**：本机 `load average ≈ 21`，且是多租户容器。
   同一 shape 连跑 5 次，`n=256/B=64` 的 mean 在 **29.5–41.5 µs** 间跳（±20%）。
   因此：小 batch 点的**绝对值**不可全信，**排序与量级**可信；`batch ≥ 64` 的大点稳定在 ±3% 内。
2. **两种统计量都报**：`docs/matrix_test_raw.md` 同时给 mean 和 min。
   mean 与 η 标定同口径；min 与 `Plan::measure` / `bench_native_npu` 同口径。
   两边在本次已对齐（`fft_check` 增加了 `(min x us)` 输出，`bench_native_npu.py` 增加了 `native_mean_us`）。
3. **GPU 数据不同源**：G1 是论坛里的 profiler 读数（未标明精度/是否含 plan），
   G2 是 cuButterfly README 的同机对照（口径最规范）。两者在 n=4096/B=1024 处交叉吻合 1.2%，
   可互为佐证；但**都不是本文实测**，跨机比较只应看量级，不应看个位数百分比。
4. **n=128/B=16 的原生均值是离群点**（462.3 µs vs min 86.3 µs），该行倍率无效。
5. **本卡 HBM 峰值未测**，本文全程用"等效带宽"这个绝对量，不用"峰值利用率"这个相对量。
