### 编译/链接硬性规则（踩过的坑）

1. `--npu-soc` 必须写成 **`Ascend910_9382`**。写 `Ascend910_93` 会直接
   `bisheng: error: Unsupported NPU architecture or soc`，随后 ccec 因
   `LLVM ERROR: PlugIn Error: no aicore arch specified` 而 abort（exit 134）。
2. **所有 ccec 选项必须放在源文件之前**。`--asc-aicore-lang` 放在 `.cpp` 后面会被
   clang 解析成 `-x asc`（语言选项），静默地**不启用 AscendC 模式**，于是
   `__gm__` / `pipe_t` 等全部未定义。
3. kernel 必须同时标注 `__global__ __aicore__ __vector__`（缺 `__vector__` 不报错但行为不正确）。
4. 参数传递只能用 `aclrtLaunchKernelWithHostArgs`。
   `aclrtLaunchKernel` → `507035`；`KernelArgsInit/Append/Finalize` → 段错误；
   `ACL_RT_LAUNCH_KERNEL_ATTR_ENGINE_TYPE` → `100000`。
5. `argBytes` 必须取 `.o` 的 `__CCE_KernelArgSize` 段（`readelf -x` 可读，
   例如 `ch4096.o` 是 24，因为 `uint32` 后有 8 字节对齐填充；手算 `8+8+4=20` 会失败）。
6. 跨 pipe 顺序用 `PipeBarrier<PIPE_ALL>()`；`PIPE_V` 只约束矢量单元。
7. `__gm__ float*` 不能隐式转成 `float*`，必须写 `__gm__ float* o = ...`。
8. `DataCopy` 的 count 是**元素数**，且 GM↔UB 要求 32B 的整数倍。
9. 启动 + 同步开销约 **21 µs**（§8.5 重新标定的 `launchUs=20.812` 口径）。

## 1. 阶段 0.3 —— 硬件能力探测

kernel：`src/ascendc/probe_hw.cpp`，host：`src/host/launch.cpp`（通用 `.o` 启动器）。

| 探测项 | 结果 | 含义 |
|---|---|---|
| `GetBlockNum()`（blocks=48 时） | 48 | `Ud_core` 可用 48 个矢量核 |
| `GetBlockIdx()` | 0..47，全部正确 | 多核一一对应 |
| `GetSubBlockIdx()` | 恒为 0 | 无子核 |
| `GetSubBlockNum()` | 恒为 1 | **每个 core 只有 1 个 AIV**，不存在 sub-block 分工 |
| `__NPU_ARCH__` | 2201 | — |

### 1.1 SIMT 编程模型：**不可用**

```
ccec ... --npu-soc=<任意值> --asc-aicore-lang --enable-simt ...
→ bisheng: error: Unsupported NPU architecture or soc: NPU soc is not supported!!!
```

在 `Ascend910_9382 / 910B4 / 910B3 / 910_9362 / 310P1 / 310P3 / 310P5 / 310P7 /
950PR_9589 / 910_93` 上逐一试过，`--enable-simt` **全部**被拒；
`-cce-enable-puresimt` 同样被拒。SIMT 头文件只有 `impl/simt_api/cpp/dav_c310/`，
且受 `#if __NPU_ARCH__ == 3510 || 5102` 门控。

> **结论（映射层）**：cuButterfly 的 `local_exchange = shuffle / warp`
> 这一支在 910_93 上**硬件不可行**。`WarpShflXorSync` 等价物只能用 UB 内
> 读写（`local_exchange = shared / register`）。这一点必须如实写进
> `H`（硬件能力）对象与合法性判据。

### 1.2 致命发现：**矢量访存的 UB 偏移必须 32B 对齐**

对 `float`，矢量算子（`Adds/Mul/Sub/Add/...`）的 `LocalTensor` **偏移量必须是 8 的整数倍**
（8 × 4B = 32B）。实测：

| 操作 | 结果 |
|---|---|
| `Adds(t0, re[0], 1.0f, 8)` | 正常 |
| `Adds(t0, re[1], 1.0f, 8)` | **507035 矢量核异常** |
| `Adds(t0, re[2], 1.0f, 8)` | 507035 |
| `Adds(t0, re[4], 1.0f, 8)` | 507035 |
| `Adds(t0, re[8], 1.0f, 8)` | 正常 |
| `Adds(re[4], re[8], 1.0f, 8)` | 507035 |
| `Adds(t0, twr[3], 1.0f, 8)` | 507035 |
| `count = 1/2/4/8/16`（偏移 0） | 全部正常 → **count 无需对齐** |

> **结论**：这条规则直接决定了蝴蝶的分块方式——上下半区 `base` 与 `base+h`
> 必须同时 ≡ 0 (mod 8)，即 **只有 h 为 8 的倍数时才能用矢量实现**；
> 旋转因子表也必须按 stage 分槽、每槽 8 对齐。h = 1,2,4 三个 stage 只能走标量。

### 1.3 次要发现：**小范围的标量 GM 写出对 D2H 不可见**

每个 block 只写 8 个 float（32B）、且各 block 的记录**首尾相接**（stride = 8 float）
时，48 个 block 中**恰好 24 个**的写入会丢失（同一 64B cache line 被两个核同时写，
回写竞争，输的一半整段丢失），且丢失是**非确定**的。

| 每 block 记录 stride | 3 次重复丢失数 |
|---|---|
| 8 float (32B) | 23 / 24 / 24 |
| 16 float (64B) | 0 / 0 / 0 |
| 32 float 及以上 | 0 / 0 / 0 |

同样地，写入地址跨度 16KB 时 8 个 float 也全部可见。

> **结论**：**每个 block 的输出区必须独占 ≥ 64B（16 个 float）的 cache line**，
> 或者输出走 `DataCopy`（MTE 通路，实测一致可靠）。
> `probe_hw` 因此改成 stride = 16 float，20 次重复 0 丢失。
> 对 FFT 来说每 block 写 2N ≥ 64 float，天然满足。

## 2. 阶段 0.1 —— 原生 `aclRfft1D` 基线

程序：`src/host/baseline_rfft.cpp`（链接 `-lopapi -lnnopbase`）。

### 2.1 调用契约（与文档/算子注册表比对后实测确认）

- 符号：`aclRfft1DGetWorkspaceSize(self, n, dim, norm, out, &ws, &exec)` +
  `aclRfft1D(ws, ws, exec, stream)`，**在 `libopapi.so`**；
  `aclCreateTensor` / `aclDestroyTensor` 在 **`libnnopbase.so`**。
- 输入：`float32`，形状 `[b, n]`。

- 输出语义 = `torch.fft.rfft(x)`（无归一化，即 `norm=None/'backward'`），
  实测 **相对误差 2.7e-7**。

## 3. 阶段 1 —— `kfft_fwd`（radix-2 DIT 复数 fp32 FFT）

- kernel：`src/ascendc/fft_radix2.cpp`
- 测试：`src/host/fft_check.cpp`（内置双精度 CPU 参考实现）

### 3.1 结构

```
GM 交错 [2N]  --DataCopy-->  UB inter[2N]
            --标量置换------>  UB re[N], im[N]      （bit-reversed，对应
                                                      cuButterfly kBitReverseInput=true）
            --for s=0..logN-1-->  h = 1<<s
                 h < 8  : 标量蝴蝶（因为 §1.2 的 32B 对齐限制）
                 h >= 8 : 矢量蝴蝶，旋转因子取自 8 对齐的 stage 槽
            --标量交错------>  UB inter[2N]  --DataCopy--> GM [2N]
```

- 并行维度：`D = batch`，`Ud_core = min(batch, 48)`，每个 block 认领
  `b = blk, blk+nblk, ...` 的若干 batch（对应 cuButterfly 的 `Ub·Tb` 循环）。
  当前 **`Us = 1`（单核内串行 stage）**，`Ts` 全驻留 UB。
- 旋转因子表（host 生成，plan 的 `G` 产物）：每个 stage 一个
  `align8(h)` 的槽，槽内第 `j` 项 = `exp(-i·π·j/h)` = `exp(-2πi·j/(2h))`，
  表长 `n + 16`。这正是 cuButterfly `butterfly.cu:1194-1201` 的公式，只是加了 8 对齐填充。
- UB 占用（n=4096）：inter 32K + re 16K + im 16K + twr 16K + twi 16K +
  t0/t1/t2 24K ≈ **120 KiB < 192 KiB** → `Ts` 可全驻留，n ≤ 4096 无需切段。

### 3.2 正确性验收（判据：maxRel ≤ 1e-4）

| n | B=1 | B=64 | B=4096 |
|---|---|---|---|
| 256 | 1.2e-7 ✓ | 1.7e-7 ✓ | 2.0e-7 ✓ |
| 512 | 1.0e-7 ✓ | 1.7e-7 ✓ | 2.1e-7 ✓ |
| 1024 | 7.1e-8 ✓ | 2.0e-7 ✓ | 2.6e-7 ✓ |
| 2048 | 4.4e-8 ✓ | 1.5e-7 ✓ | 2.2e-7 ✓ |
| 4096 | 6.0e-8 ✓ | 1.5e-7 ✓ | 2.6e-7 ✓ |

**15/15 全部通过**，最好比判据严 3 个数量级。

### 3.3 当前性能（仅供后续阶段对比，非验收项）

| n | B | us/call |
|---|---|---|
| 256 | 64 | 100 |
| 256 | 4096 | 3420 |
| 4096 | 64 | 1393 |
| 4096 | 4096 | 58967（阶段 1 旧版本值；同一 v1 后续复测见 §6.5 = 49 336） |

等效带宽只有约 **4.5 GB/s**（实测可达 1265 GB/s），瓶颈明显是两处标量循环
（bit-reversal 置换、planar→交错）加上 h=1,2,4 的标量 stage。
`PipeBarrier` 不是瓶颈（把 stage 间 `PIPE_ALL` 换成 `PIPE_V` 后耗时基本不变）。

## 4. 对后续阶段的直接影响

1. **`H` 对象必须写明**：无 SIMT、无 sub-block、UB=192 KiB/AIV、
   48 矢量核、矢量 UB 偏移 32B 对齐、单 block 输出 ≥ 64B cache line。
   → `local_exchange ∈ {shared, register}`；`Us = 1`（跨核 stage 流水要走 GM + `CrossCoreSetFlag`，
   属 `hardware-infeasible` 或需单独评估）。
2. **`A` 对象**：`Ud = 128(fp32 lane) × 48(AIV)`，`Td → batch 分块循环`，
   `Ts → UB 驻留 + stage 循环`，`Ub → 每 block 认领的 batch 数`。
3. **`P` 对象**：`stage_fusion`（radix-4/8）与对齐规则天然耦合——
   h=1,2,4 必须合并成 radix-8 才能整体矢量化，这正是阶段 3 的头号优化点。
4. **`L` 对象**：planar(re/im) 已验证正确；交错进出靠 `DataCopy`。
   下一步优化用 `DeInterleave` / `Interleave` / `Gather` 替换标量置换。
5. **`Q` 对象**：基线（原生 `aclRfft1D`）与 `torch.fft.rfft` 参考已就绪，
   阶段 5 的测量矩阵可以直接接上。

### 5.2 冒烟测试踩到的三个坑（都已修）

1. **`refFft` 就地置换自食其果**：`a[i] = a[rev[i]]` 边读边写会读到已改写的数据 → 先 `orig = a` 再置换。
2. **`maxRel` 归一化写错**：逐元素除以 `|ref[i]|` 会把 `ref≈0` 处的浮点噪声放大到 1e6 量级 → 与 `fft_check` 一致，改用**全局 scale**（`max|ref|`）。
3. **`Plan::measure()` 把 I/O 也计进去了**：每次 `run()` 都做 H2D+D2H，n=4096/B=4096 时是 2×33.5 MB 的**可页内存**拷贝，实测 ~16.7 ms —— 正是把 49.3 ms 的 kernel 测成 66 ms 的元凶。改为「先跑一次准备数据，再循环 `launch+sync` 计时，D2H 放到计时之外」。修正后 `measure()`=27975 µs 与 `fft_check`=27938 µs 差 **0.1%**。

### 5.3 验收

15/15 PASS（n∈{256,512,1024,2048,4096} × B∈{1,64,4096}），`maxRel ≤ 1.6e-7`。
`estimate()` 修正显存单位后（`gmNsPerByte` 早期误用 71 ns/字节，实为 ns/KB，把 η 放大 ~1000×），η 与实测差 **≤20%**，排序可信。

## 6. 阶段 3 —— 性能：8-plane 布局矢量化 h=1,2,4

### 6.1 分段计时（n=4096, B=4096, 48 AIV）

用 `PHASE_VEC_ONLY` / `PHASE_SCALAR_ONLY` 把 stage 拆开测（单位 µs/次）：

| 变体 | 耗时 | 含义 |
|---|---|---|
| FULL | 49 361 | 全部 |
| VEC_ONLY（跳过 h=1,2,4） | 26 372 | → h=1,2,4 占 **22 989 µs = 46.6%** |
| SCALAR_ONLY（跳过 h≥8） | 43 324 | → h≥8 占 **6 037 µs = 12.2%** |
| 其余（位反转+交错+显存） | 20 335 | 41.2% |

**结论：h=1,2,4 是唯一的大头。**

### 6.2 为什么这三级只能标量

实测硬规则：**矢量算子的 `LocalTensor` offset 必须是 8 float（32 B）的倍数**，否则 AIV 抛 `507035`。
planar 布局下 stage `h` 的高半区 offset = `base + h`，`base = 2h·g`：
- h=1 → offset 奇数；h=2 → ≡2 (mod 4)；h=4 → ≡4 (mod 8) —— 全部非 32 B 对齐。
- h≥8 → `base+h` 恒为 8 的倍数 ✓

且**加任何常数位移都救不了**（h=1 要求 `base≡7 (mod 8)` 与 `base` 为偶矛盾）。

### 6.3 解法：把下标高 3 位当 plane

```
pos(j) = (j & 7) * (n/8) + (j >> 3)
```
于是 stage h∈{1,2,4} 的蝶形两端落在**同一 tile、不同 plane**：

| h | plane 对 | twiddle（每对是常数） |
|---|---|---|
| 1 | (0,1)(2,3)(4,5)(6,7) | `w=1` |
| 2 | (0,2)(4,6) / (1,3)(5,7) | `w[0]=1` / `w[1]=-i` |
| 4 | (0,4)(1,5)(2,6)(3,7) | `exp(-i·π·p/4)` |

- plane 基址 = `p*(n/8)`，要求 `n/8 ≡ 0 (mod 8)` ⇒ **n ≥ 64 且为 64 的倍数**（框架据此判 infeasible）。
- twiddle 对每对 plane 是**标量常数**，用 `Muls` 就能做复数乘，无需 twiddle 向量。
- 三个 stage 后用 `Gather` 按索引转回 planar，h≥8 沿用原路径。

### 6.4 API 可用性（arch 2201 实测/读码确认）

| API | 2201 可用？ | 证据 |
|---|---|---|
| `Interleave` / `DeInterleave` | **不可用** | `kernel_operator_vec_duplicate_intf.h` 里被 `#if (__NPU_ARCH__ == 3510) \|\| (__NPU_ARCH__ == 5102)` 整段包住 |
| `Gather(dst,src,srcOffset,srcBaseAddr,count)` | **可用** | 无 arch 守卫；`dav_c220/kernel_operator_vec_gather_impl.h` 有实现 |
| `Transpose(dst,src,tmp,params)` | 部分 | B16 转置在 2201 上只支持 `uint16_t`，不支持 fp32 |
| `Mmad` / `Fixpipe` | 见 §6.6 第 4 条 | Mmad 是静默空操作，矩阵单元从 AIV kernel 不可达 |

**`Gather` 单位探针**（`src/ascendc/gather_probe.cpp`，一次性写入即可确定）：
- `srcOffset[i]` 单位 = **字节**
- `srcBaseAddr` 单位 = **字节**
- `count < 64`（fp32）走单 repeat + mask，`count = k·64` 走 `repeatTime = k`

## 7. 阶段 3+ —— Gather 取代标量散射（27.8 ms → 7.6 ms）

### 7.1 消融（n=4096, B=4096，8-plane 内核上逐项关闭）

| 关掉的项 | 节省 | 占比 |
|---|---|---|
| planar→交错（最后那次标量 `SetValue` 环） | 9 790 µs | **35.1%** |
| h≥8 的 planar 级 | 6 434 µs | 23.1% |
| 位反转散射改 Gather | 282 µs | 1.0% |

**结论：最大头不是蝶形计算，是收尾那圈标量写回。**

### 7.2 解法：索引全部由 host 预生成，kernel 只调 `Gather`

`Generator` 新增三个索引生成器，`prepare()` 拼成**单个 4n 的 GM 张量**一次下发：

| 段 | 长度 | 含义 |
|---|---|---|
| `idxB` | `n` | 位反转 + 去交错：`plane[k] ← in[bitrev(invpos(k))]`，字节偏移 `8·bitrev` |
| `idxT` | `n` | plane → planar 转置：`planar[k] ← plane[pos(k)]` |
| `idxO` | `2n` | planar → 交错输出：`out[2j]←plan[j]`、`out[2j+1]←plan[n+j]` |

kernel 侧只剩 3 次 `Gather` + 1 次 `DataCopy`，标量环全部消失。
`buildArgs()` 由 4 指针扩到 5 指针（`argBytes = 56`）。

## 8. 阶段 4 —— K-plane 推广（7.6 ms → 3.76 ms）

### 8.1 为什么 op 次数是唯一有效的杠杆

微基准（同一批内核、只改长度与缓冲布局）给出的成本模型：

```
cost ≈ 13.3 ns × (#矢量算子调用次数) + 0.023 ns × (元素访存数)
```

- 短缓冲（10 次 × 长度 8）：0.182 µs/迭代 → **18 ns/op**，几乎全是发射开销。
- 真实布局（8 缓冲、256 组）：54.5 µs（1 blk）/ 58.5 µs（48 blk）→ 与 1 blk 几乎相同 ⇒ **多核并发几乎免费，缩短循环才是收益来源**。
- 完整 9 级循环 91.2 / 96.1 µs ⇒ `PipeBarrier<PIPE_V>` 插在组循环里只值 ~395 µs。

所以优化目标是**减少 `#op`，不是减少每次 op 的长度**。

### 8.2 为什么 8-plane 只是特例

8-plane 只矢量化了 h=1,2,4（log 3 级）。推广到 K-plane：把下标**低 `logK` 位当 plane**：

```
pos(j) = (j & (K-1)) * (n/K) + (j >> logK)        // 行 = (j>>logK)，列 = j 的低 logK 位
```

- stage `h` 能走平面路径 **当且仅当 `2h | K`**（即 `h ≤ K/2`），此时恰好 `K/2` 对行，每对 op 长度 `rows = n/K`。
- 每级 op 数：`14 × K/2 = 7K`（h=1 时旋转因子恒 1，走 10 算子分支 → `5K`）。
- 平面级共 `logK` 级；`h ≥ K` 的各级仍走 planar，op 数 `5n/h`。

于是总 op 数是 K 的函数，且**最优点随 n 变**：

```
ops(K) = 5K + 7K(logK-1) + 5n·Σ_{s=logK}^{logn-1} 2^{-s}
          \___ 平面级 ___/   \_______ planar 级 _______/
```

平面级那项**与 n 无关**（只取决于 K），planar 那项 ≈ `10n/K`。所以小 n 必须取小 K：

| n | K=8 | K=16 | K=32 | 择优 |
|---:|---:|---:|---:|:---|
| 256 | **462** | 566 | 1 126 | 8 |
| 512 | 782 | **726** | 1 206 | 16 |
| 1024 | 1 422 | **1 046** | 1 366 | 16 |
| 2048 | 2 702 | 1 686 | **1 686** | 32（平局实测 32 更快） |
| 4096 | 5 262 | 2 966 | **2 326** | 32 |

约束：`rows = n/K ≥ 8` 才满足 32 B 对齐规则 ⇒ `K ≤ n/8`，且 `K ≤ 32`。

**规则由 `include/butterfly/fft_k.hpp` 的 `bfly::planeKFor(n)` 单点定义**，
内核、`fft_check`、框架 `Generator::planeK` / `estimate()` 四处共用同一份头文件
（ccec 下需带 `[aicore]` 属性，用 `BFLY_AICORE` 宏在设备/宿主编译间切换）。

> 第一版规则写成 `n>=256 ? 32 : (n>=128 ? 16 : 8)`，导致 n=256 从 621 µs 退化到 1 286 µs（**慢 2.1×**）——
> 表面上 K 越大 op 越少，实际小 n 上平面级 `7K(logK-1)` 直接压垮 planar 级的节省。

### 8.3 过程中踩到的坑

- **Python 先行仿真**：先用 numpy 把整条流水线（位反转→平面级→转置→planar 级→交错）按 K=8/16/32 各跑一遍，全部 PASS（`maxRel ≤ 5e-8`），证明**算法无误**，bug 只可能在 C++/宿主侧。
- 真实 bug：`scripts/build.sh kernel check` 只取 `$1`，`check` **根本没重编**，`fft_check` 仍在生成 K=8 的索引而 kernel 已用 K=16/32 ⇒ 表现为 `maxRel ≈ 0.5~0.9`。
  修复：`build.sh` 改为 `t=${*:-all}`；同时补回被上次批量替换误删的 `Generator::genInterleave`。
- **`__aicore__` 不能修饰自由函数**：把 `planeKFor` 放进头文件后，ccec 报
  `reference to [host] function 'planeKFor' in __global__ function`，`__aicore__` 也报
  `unknown type name`。正确写法是 CCE 的裸属性 **`[aicore]`**（`CCE_INTRINSIC` 宏里就是这么用的），
  宿主编译（g++）时该宏展开为空。见 `BFLY_AICORE`。

### 8.4 结果（B=4096，reps=20）

| n | 阶段 3++ (µs) | 阶段 4 初版 `K=min(32,n/8)` | 阶段 4 择优 K | 最终 vs 阶段 3++ |
|---:|---:|---:|---:|---:|
| 128 | — | 593.3 | **406.4** | — |
| 256 | 621 | 1 285.7 ❌ | **626.4** | ≈1.00× |
| 512 | 1 044 | 1 411.2 ❌ | **931.2** | 1.12× |
| 1024 | 1 940 | 1 663.4 | **1 399.9** | 1.39× |
| 2048 | 3 708 | 2 228.9 | **2 225.8** | 1.67× |
| 4096 | 7 607 | 3 750.0 | **3 765.0** | **2.02×** |

小 batch（reps=20）：n=4096 的 B=1 → 63.7 µs、B=64 → 107.2 µs（阶段 3++ 分别为 109.4 / 200.1）。

- **正确性 15/15 PASS，`maxRel ≤ 1.6e-7`**；`test_framework` 亦 PASS。

### 8.5 η 估算器重新标定

`estimate()` 原来按 Phase 1 的标量/矢量分项硬编码，与当前内核完全脱节
（`test_framework` 曾报 `eta=681.6 vs measured=107.2`，**高估 6.4×**）。

改为**结构化计数 + 最小二乘**：

```
η = launchUs + ceil(B/udCore) × (opNs × 算子调用数 + elemNs × 元素访存数)
```

- 算子/元素按 `fft_radix2.cpp` **逐条数出**（平面级 `3K+5K(logK-1)`，planar 级 `5n/h`，收尾 6 次），不是拟合出来的形状。
- 标定集：`n ∈ {128,1024,4096}` × `B ∈ {48,96,192,384,768,1536,4096}`，reps=20（**剔除 B=1**，它含额外单次启动开销），
  脚本 `scripts/calib_eta.py` 可复现。
- 阶段 5 换内核后**重新拟合**得 `launchUs=20.812`、`opNs=12.0`、`elemNs=0.050`
  （阶段 4 的旧值为 22.165 / 11.6 / 0.052——**形状没变**，说明算子计数是唯一在动的量）；
  `opNs=12.0` 与微基准的 13.3 ns/op 相互印证。
- **残差平均 3.8%、最大 15.7%；留一交叉验证（LOO）平均 4.3%、最大 16.8%**（最大点为 n=1024/B=96 的噪声点）。
- 实测：`test_framework` 报 `eta=96.1 vs measured=93.6` ⇒ **误差 2.7%**。
- K 择优也随公式更新重算（`planeKFor` 改用新算子计数）：n=128..4096 的取值**一个都没变**（已用 C++/Python 双实现对 8 ≤ n < 200000 全量比对）。

## 9. 阶段 5 —— 蝶形就地写回 + 屏障消融（3.76 ms → 3.28 ms）

§10.2 已指出瓶颈是矢量算子的 `#op`，阶段 5 只做两件事——**减少算子调用数**、**减少流水屏障**，
并且每一项都先单独消融再合入。

### 9.1 消融（n=4096, B=4096, reps=10；四个变体各自独立编译）

| 变体 | 改动 | 耗时 (µs) | vs 基线 | 正确性 |
|---|---|---:|---:|:---|
| 基线 | 阶段 4 终态 | 3 758.7 | 1.00× | PASS |
| A | 删掉循环内全部 3 处 `PipeBarrier<PIPE_V>` | 3 664.1 | −2.5% | PASS |
| B | 蝶形就地写回（8 算子 → 4 算子） | 3 382.4 | **−10.0%** | PASS |
| **C = A + B** | 合并 | **3 293.3** | **−12.4%** | PASS |

**就地写回**——矢量算子允许就地读写（逐元素独立），这是把平面级 14 算子/对砍到 10、
h=1 级 10 砍到 6 的关键：

```cpp
// 旧：Add(t0,rp,t2); Sub(t1,rp,t2); Adds(rp,t0,0); Adds(rq,t1,0);  + im 同构 = 8 算子
Sub(rq, rp, t2, rows);    // rq = rp - t2
Add (rp, rp, t2, rows);   // rp = rp + t2
Sub(iq, ip, t3, rows);
Add (ip, ip, t3, rows);   // 共 4 算子
```

三处必须同步更新：`src/ascendc/fft_radix2.cpp`、`include/butterfly/fft_k.hpp` 的 `planeKFor`、
`src/framework/butterfly.cpp` 的 `estimate()`。

| 项 | 阶段 4 | 阶段 5 | 变化 |
|---|---:|---:|---:|
| 平面级算子公式 | `5K+7K(logK-1)` | `3K+5K(logK-1)` | — |
| n=4096 算子/批 | 2 326 | **2 012** | −13.5% |
| n=4096 元素访存/批 | 311 296 | **270 336** | −13.2% |

- 单点 −10% ~ −12.4%，**18 点全网格 PASS**（reps=20）。
- n=4096/B=4096：3 765 → **3 284 µs**；累计 **v1 → 当前 49 352 / 3 284 = 15.0×**。

### 9.2 屏障精细化：只有"不安全"的改法才有收益

把 8 处 `PipeBarrier<PIPE_ALL>` 逐个降级成 `PIPE_V` / `PIPE_MTE2`，
每处**单独**消融，用 n=128/B=64（竞争最敏感）+ n=4096/B=4096（性能最敏感）双点验收。
8 处 = 下表 6 处，另加 prologue（旋转因子与三张索引 `DataCopy` 之后、批循环之前，
现 `fft_radix2.cpp:123`）与批尾 `DataCopy(gout,·)` 之后的批间屏障
（该屏障第二批已删，见 `docs/性能优化-C2b与K择优.md` §6；prologue 见同文档 §11.4）：

| 位置 | 降级为 | 结果 |
|---|---|---|
| 输入 `DataCopy(plan, gin)` 之后 | `PIPE_MTE2` | ❌ **FAIL**（n=128/B=64 竞态，`maxRel` ~1e22） |
| 末尾 `Gather` → `DataCopy(gout, ar)` 之间 | `PIPE_V` / `PIPE_MTE2` | ❌ **FAIL**（两者都不够，**必须 PIPE_ALL**） |
| 其余 4 处（阶段与阶段之间） | `PIPE_V` | ✅ PASS，但 **+0%（在噪声内）** |

唯一的"提速版"（3 176 µs，−3.6%）正是把输入 `DataCopy` 后的屏障错降成 `PIPE_MTE2` 的那一版——
**那点收益全部来自跳过了一次真实的等待**。
结论：合法的屏障降级一分钱赚不到；阶段 5 终态保留全部 `PIPE_ALL`，并把"屏障不是可优化项"写死。

### 9.3 K 扫描：`#op` 模型被独立验证

强制 `planeKFor` 返回 K = 8 / 16 / 32（内核与 `fft_check` 同步重编译），reps=10：

| n | K=8 | K=16 | K=32 | 模型 `#op`（K=8/16/32） | 模型最优 |
|---:|---:|---:|---:|---|---|
| 4096 | 7 145 | 4 340 | **3 293** | 5 194 / 2 817 / **1 986** | K=32 ✓ |
| 1024 | 1 787 | **1 215** | 1 295 | 1 117 / **538** / 796 | K=16 ✓ |

两个 n 上的排序与单调性都与逐条数出的 `#op` 完全吻合——`estimate()` 的 K 择优因此可信。

### 9.4 radix-4 / radix-8 融合：**不采纳**（原计划第 1 条被数据否掉）

把 planar 级按"融合的 R 点分组蝶形"重写（矢量长度 h、组数 `n/(Rh)`），逐条数出每组矢量算子数：

**每组算子数** `g(R) = 6(R−1) + 2R·log2R`
（`6(R−1)` = 每组 `R−1` 次复乘的实数形式；`2R·log2R` = `log2R` 层 radix-2 蝶形网络的实数加减）

| 形式 | `g(R)` | 覆盖的 radix-2 级 | 基准（分开，按最大长度 h 折算） | 融合后 | **相对 `#op`** |
|---|---:|---|---:|---:|---:|
| radix-2（现状） | 10 | 2 级（h, 2h） | `5n/h + 5n/2h` = **7.5n/h** | — | 1.00× |
| radix-4 融合 | **34** | 2 级（h, 2h） | 7.5n/h | `34·n/(4h)` = **8.5n/h** | **1.13×（+13%）** |
| radix-2（现状） | 10 | 3 级（h, 2h, 4h） | `5n/h+5n/2h+5n/4h` = **8.75n/h** | — | 1.00× |
| radix-8 融合 | **90** | 3 级（h, 2h, 4h） | 8.75n/h | `90·n/(8h)` = **11.25n/h** | **1.29×（+29%）** |

> 早先的草稿把 radix-4 写成"40 ops / +33%"，是漏算了 `2R·log2R` 里 radix-2 网络的加减由
> 3 次复加（=12 实数加减）改为 2 层 4 点网络（=16）的差异，正确值是 **34 / +13%**——**结论不变**。
> 注意这里比的是"融合后覆盖同样多的 radix-2 级"，而不是把每一级单独比（那样会把长短算子混为一谈）。

算术量两者完全相同（每级仍是 3 次复乘 + 4 次复加的实数形式），差别全在**融合把长度 `2h`、`4h`
的长算子拆成了长度 `h` 的短算子**；而 §8.1 已实测 `#op` 是固定发射开销、与 op 长度几乎无关
（13.3 ns/op 在 op 长度 16 到 4096 之间几乎不变）——**长算子更划算，短算子调用次数多就是输**。
radix-4 唯一能省的是每组的 `PipeBarrier`，而 §9.2 已证明屏障不是瓶颈。

> §11.3 把上面这组 `g(R)` 系数接进了 η 估算器：`opFactor = (g(R)/(R−1))/10`、
> `elemFactor = (g(R)/(R·log2R))/5`，`R=2 → 1.00/1.00`、`R=4 → 1.13/0.85`、`R=8 → 1.29/0.75`。
> 也就是说 **η 已经能如实反映"radix 越大算子越少但调用越多"**，而不必先去实现 kernel。

**结论：在"算子发射受限"的 AIV 上，radix 提升（cuButterfly 的 `F` 对象）是负收益。**
只有当未来 `#op` 被双缓冲流水线摊平时才需要重估。

> ⚠️ **2026-09-30 补注：本节的否决只对 planar 级成立，平面级已被实测推翻。**
> 两处问题：
> 1. `g(R) = 6(R−1) + 2R·log2R` 把**复数乘按 6 个实数算术**计入、蝶形却按**矢量调用**计入，
>    **单位不一致**。C2b（复数乘 6→4 个矢量调用）之后，非平凡 radix-4 是 **28 不是 34**。
> 2. 更关键：本节假设「融合把长度 `2h`/`4h` 的长算子拆成长度 `h` 的短算子」——
>    这对 **planar 级**成立（那里的矢量长度 = group 尺寸），但**平面级的矢量长度是
>    `rows = n/K`、与 `h` 无关**，融合既不缩短算子也不增加调用次数。
>
> 实测（`docs/性能优化-C2b与K择优.md` §9）：平面级 radix-4 算子 226 → 164（−27.4%）、
> n=4096/B=4096 实测 **−5.3%**（−5.3% = 耗时减少）。planar 级融合**未做**：
> 该文 §10.3 逐对重算 = **+68 算子 / −17,744 元素 ≈ 耗时 −0.9%**（估算；早先的
> +51 算子 / −12,288 元素 ≈ −2.1% 漏算了融合级自身的 28 算子），收益太小而复杂度与风险高
> —— 故本节的否决对 planar 依然有效。

### 9.5 阶段 5 之后还剩什么

- ✅ 就地写回（−12.4%）、屏障消融（结论：不可做）、K 择优（已最优）、radix 融合（已否决）。
- ❌ **输入双缓冲**：UB 只剩 7.3 KiB 余量（184.7 / 192 KiB），放不下第二个 `plan+plane`。
- ⬜ `D>1` 跨 batch 流水 / `Ts` 折叠——框架设计项，未做。
- ⬜ **对照 §10.1**：B=4096 仍落后原生 1.43×（n=4096）~ 4.35×（n=256），差距只能靠
  "把 `#op` 再砍一半"或"把 12 ns/op 摊到 0"，前者已无低成本手段，后者需要更深的流水重构。

## 11. 阶段 6 —— 设计空间 / η / 选型闭环真正可用

> 阶段 2 交付的是**骨架**，四件事是假的：
> 1. `DesignSpace::load` 只把 JSON 读进 `raw` 留档，**8 条轴全部用代码里的硬编码默认值**；
> 2. `enumerate()` 不给任何候选标 `Infeasible` —— 运行时打印 `infeasible=0`，864 个候选全是"可行"；
> 3. `Context::select()` 注释写着"前 K 个里选 η 最小的"，实际 `return makePlan(*order[min(size, topK)-1])`
>    —— 取的是**第 K 名**，而且**从不实测**，η 打平的候选只能靠顺序撞；
> 4. `Plan::measure()` 在可能未初始化的 `devIn` 上跑 kernel，`maxRelErr` 直接抄 `cand_.q`（本来就是 0），
>    `State` 一步跳到 `Measured`。
>
> 阶段 6 把这四条做成真的。

### 11.1 设计空间 JSON 真正生效（864 个候选）

- 匿名命名空间新增 `findArray / toArray / toStringArray`（`src/framework/butterfly.cpp`），
  `DesignSpace::load` 从 JSON 解析 **8 条轴**：`ud_core` / `radix` / `fusion_level` /
  `local_exchange` / `in` / `out` / `ts` / `coefficient_residency`；`applyDefaults()` 只在轴缺失时兜底。
- 新增 `DesignSpace::pointSize(radix, fusionLevel) = radix^fusionLevel`（`F` 对象的**等效蝶形点数 R**），
  枚举、η、选型三处共用同一个定义，避免各写各的。
- **踩坑（第一次跑就是 864/864 全不可行）**：`toArray` 用 `atoi` 解析 token，而 JSON 里写的是
  `"coefficient_residency": [true]` → `atoi("true") == 0` → **所有候选都判成 `cr=false`**，
  被 `coefficient_residency` 那条判据成批杀掉。修法：`toArray` 显式把 `true/false` 映射成 1/0。
- 组合数与 JSON 逐条核对：`4 ud × 3 radix × 3 fs × 2 ts × 1 cr × 3 lx × 2 in × 2 out = 864` ✓

### 11.2 四态枚举：不可行判据落地（n=4096 → 816 Infeasible / 48 Feasible）

判据按代码里的**检查顺序**执行，日志按 `reason` 归并计数：

| # | 判据 | n=4096 计数 | reason 文本（节选） |
|---|---|---:|---|
| 1 | `Mapping::validate`：`ud_core>vector_core_num` / `level!=0` | 0 | — |
| 2 | `local_exchange=shuffle` 需要 SIMT（§1.1 已证本 SoC 不可用） | **288** | `local_exchange=shuffle requires SIMT; not available on this SoC` |
| 3 | `StagePlan::fits`：UB 超 192 KiB | 0 | — |
| 4 | `n < 64`（8-plane 布局要求 `n/8` 为 8 的倍数） | 0 | `plane layout needs n>=64 (tiles=n/8 must be 8-aligned, 32B rule)` |
| 5 | `R = radix^fs` 非 2 的幂 / `R ∤ n` / **`R > min(K, n/K)`** | **192** | `R=64 exceeds usable butterfly width min(K=32, n/K=128)=32`（×128）+ `R=512 …`（×64） |
| 6 | `coefficient_residency != true` | 0 | JSON 只给了 `[true]` |
| 7 | `ts != 1`（内核要求 twiddle/索引跨 batch 常驻） | **192** | `kernel assumes ts=1 (twiddles + indices resident across the batch loop); ts=0 needs a per-batch GM reload` |

| | **Infeasible 合计** | **816** | |
| | **Feasible（停在 `Unverified`）** | **48** | |

第 5 条是新的：`R` 蝶形组必须同时放得进 plane 区（宽 `K`）和 planar 区（行 `n/K`），
`widthCap = min(K, n/K)`；n=4096 时 `K=32`、`n/K=128` → `widthCap=32`，
所以 `radix=4,fs=3`（R=64）、`radix=8,fs=2`（R=64）、`radix=8,fs=3`（R=512）全部出局。

**边界情形也落地了**：`n=16/32` → `infeasible=864, feasible=0` → `select()` 返回 `nullptr`，
测试打印 `no feasible candidate` 并以非 0 退出（此前是"随便挑一个然后跑挂"）。

### 11.3 η 的 radix 结构因子（`F` 对象进 η）

`R=2` 的精确计数不变（§8.5 标定的常数照用），新增 R≠2 的结构缩放：
对 planar 级，`R` 点分组（矢量长度 h、组数 `n/(Rh)`）的每组算子数
`g(R) = 6(R−1) + 2R·log2R`（§9.4 推导），于是

```
opFactor   = (g(R) / (R−1)) / 10        // 对齐 radix-2 的 10
elemFactor = (g(R) / (R·log2R)) / 5     // 对齐 radix-2 的 5
```

> ⚠️ **本表为旧口径（旧分母 `/10`、`/5` 与旧系数 `g(R) = 6(R−1) + 2R·log2R`），已被 §9.4 补注与
> `docs/性能优化-C2b与K择优.md` §9.4、§9 实测推翻：C2b 之后非平凡 radix-4 是 `g=28` 不是 34、
> `opF` 已改为 `= elF`（R=4：1.1667 → 0.875），且平面级 radix-4 实测 **−5.3%**。本表仅作历史记录。**

| R | `g(R)` | opFactor | elemFactor | η(n=4096, B=64) | 相对 R=2 |
|---:|---:|---:|---:|---:|---:|
| 2 | 10 | 1.00 | 1.00 | **96.1 µs** | 1.00× |
| 4 | 34 | 1.13 | 0.85 | 99.0 µs | **+3.0%** |
| 8 | 90 | 1.29 | 0.75 | 103.2 µs | **+7.4%** |

即 **η 如实反映了 §9.4 的结论**：radix 提升"算子少一点但调用多一点"，净效果是**变慢**——
而不必先把 R≠2 的 kernel 写出来才看得到这个结论。
**已声明的假设**：plane 区（h=1..K/2）按同一比例缩放；plane 区的 32B 对齐规则会随 R 重推，
所以这是**结构估算，不是实测**（代码注释里也写了这一点）。

### 11.4 选型闭环：构 plan → 正确性验收 → 计时 → 取实测最优

- **`makePlan`**：只接受 `R == 2`（只有 `kfft_fwd`），其余返回 `nullptr`。
  此前内核一律无条件加载 `kernelPath_` 并跑 radix-2 —— R=4/8 的候选会"静默跑对了的假结果"。
- **`select`**：η 排序 → 逐个取最多 `topK` 个 → `makePlan` → `measure` → 回填 `Metric`/`State`
  → 取 `measuredUs` **最小**者。日志逐条打印 `accept / reject / skip` 及原因，例如
  `skip r4_ud48_ts1_register_f1_R4 eta=99.0 no kernel for R=4 (only R=2 implemented)`。
- **`measure` 的状态推进（四态真的在走）**：
  1. 起点 `Unverified`；
  2. **正确性**：最多 4 个 batch，与 `bfly::refFftF32`（双精度 DIT）按 `maxRelScaled`（全局 scale 归一，
     判据同 `Q.acceptance.max_rel_err = 1e-4`）比对 → 通过置 `Feasible`；
     不通过留在 `Unverified`、写 `reason`、返回 `−7`（`select` 里打印 `reject …`）；
  3. **计时**：warmup 1 次 + **10 次逐次 launch 取最小值** → `Measured`，真实 `maxRelErr` 回填 `Metric`。
- **参考实现收敛到一处**：`include/butterfly/reference.hpp` + `src/framework/reference.cpp`
  （`refFftF32` / `maxRelScaled` / `patternAt`）。`tests/test_framework.cpp` 删掉它自己那份 `refFft` 拷贝，
  改用同一份 —— 框架内部验收和外部交叉验证用的是同一把尺子。
- **踩坑（计时统计量选错会编故事）**：先用 `reps=5` 取均值，两个**内核完全相同**的候选
  （`localExchange` 内核根本不读）被测出 **119.8 vs 99.2 µs** 的假差异，选型据此"选对了"其实纯属运气。
  改成"逐次 launch 取最小值"后是 93.9 vs 92.0 µs（2%）。`min` 是 kernel 计时的常规统计量，
  对页缺/同步抖动鲁棒；η 仍是按 `fft_check` 的 `reps=20` 均值标定的，两者口径差异见 §11.5。
