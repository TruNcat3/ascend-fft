# 端到端对比：H2D + 变换 + D2H（自研 vs CANN 原生 vs 裸 CANN C API）

> 硬件 Ascend910_9382（48 AIV）；reps=10；`--rounds 3` 逐点 min-of-means（与 `matrix_test.py` 同口径）。

> **口径**（三路逐段对应，计时区外均剔除进程/框架启动与输入生成）：
> 1. `自研` = H2D → `kfft_fwd` → D2H（复数→复数，`fft_check AB_E2E=1`）
> 2. `原生` = `xd.copy_(x_cpu)` → `torch.fft.fft(xd)` → `yd.copy_(out)`（复数→复数，torch_npu op-plugin 内核）
> 3. 三路主机缓冲默认 **pinned**（`AB_E2E_HOST`；自研/裸 `aclrtMallocHost`，torch `.pin_memory()` + 预分配 pinned 目的张量），`AB_E2E_HOST=pageable` 为受限对照
> 4. `裸 CANN` = H2D → `aclRfft1D` → D2H（**实→复、单边**，唯一可用的裸 CANN C API FFT —— CANN 9.0.0 没有复数→复数 C API）
> 
> **表1 的 `E2E 比值 > 1` 表示自研更快**；只算 kernel 的 `device 比值` 见 `matrix_test_a7.md`。**表2 仅作参照、不参与胜负统计**：
> * 变换不同（实→复 vs 复→复），且 **搬运量正好是一半**（`8n·B` vs `16n·B` 字节），大 batch 的 E2E 不可直接比；
> * 它的价值在 **device-only**：与传输无关，用来把「CANN 算子调用路径的固定开销」和「torch 调度 + op-plugin」分开。

> `裸 冷首调` 见 JSON 的 `bare_first_us`：裸一路是**单进程单 shape**，每个 shape 都要从头建图，与 `原生 冷首调`（单进程跑完 49 点、plan cache 跨 shape 复用）**口径不同，不可直接比**。

## 汇总

- 正确性：**49/49 PASS**（maxRel ≤ 1e-4）
- **device-only**：49/49 点自研更快，几何均值 3.17x
- **端到端 E2E**：46/49 点自研更快，几何均值 1.66x
- **裸 CANN `aclRfft1D`**（实→复，仅参照，49/49 点）：device 几何均值 **189.5 µs**、E2E 几何均值 **305.0 µs**；`原生 device ÷ 裸 device` 几何均值 **0.67x**（两路变换不同，只看固定开销量级）
  - 小 batch（`B ≤ 64`，传输可忽略）：裸 device **164.0 µs** vs 原生 **97.7 µs** vs 自研 **22.3 µs** —— 固定开销在 CANN 调用路径本身，不是 torch 层
- E2E 最快点 **2.70x** @ n=512/b=4，最慢点 **0.95x** @ n=1024/b=4096
